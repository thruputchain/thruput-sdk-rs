### [sdk-auth/footgun] ReceiveAuthHandles for [T; N] is a no-op, silently dropping/misassigning Signed handles in arrays

**File:** `crates/sdk/src/receive_auth_handles.rs:60`

The fixed-size-array impl returns Ok without touching elements: `impl<T: ReceiveAuthHandles, const N: usize> ReceiveAuthHandles for [T; N] { fn receive_auth_handles(&mut self, _handles: ...) -> ... { Ok(()) } }`. Every sibling container iterates elements: the `[T]` slice impl (line 93), Vec, VecM, heapless::Vec, and crucially both `CollectAuthHandles for [T; N]` (collect_auth_handles.rs:52, which iterates and pushes handles) and `Mintable for [T; N]` (mintable.rs:282, which mints one child token per element). So `[Signed<X>; N]` is fully supported on the mint/collect side but never receives handles. Derived `#[contract_type]` structs recurse per field (macros/src/contract_type.rs:234), so any struct with an array-of-Signed field hits this. Consequences: in `Signed::consume` (signer.rs:334-337) there is no leftover-handle check, so the array elements keep the u32::MAX sentinel and any Signed field declared AFTER the array receives the array's handles — auth tokens silently assigned to the wrong fields. In the entrypoint path the strict check in receive_auth_handles_from_slice turns this into a confusing runtime 'unexpected auth handle remaining' error for a type the SDK otherwise supports.

> Verifier: Every factual claim checks out against the code. (1) crates/sdk/src/receive_auth_handles.rs:60-68: `impl<T: ReceiveAuthHandles, const N: usize> ReceiveAuthHandles for [T; N]` ignores the iterator (`_handles`) and returns Ok(()) — a genuine no-op, unlike the noop macro cases which are leaf scalar types. (2) Every sibling container in the same file iterates: `[T]` at line 93, VecM at 107, heapless::Vec at 132, Vec at 181, tuples at 191+. (3) The mint/collect side fully supports arrays: collect_auth_handles.rs:52-63 iterates `[T; N]` and pushes each element's handles, and mintable.rs:283 (`Mintable for [T; N]`) mints one child per element via `preimage.map`. So `[Signed<X>; N]` compiles and works on the produce side (Signed<T> implements CollectAuthHandles unconditionally at signer.rs:136) but is silently skipped on the receive side — nothing in the type system prevents this, and there is no doc comment on the impl, in the module, or in any README warning about arrays of Signed. (4) The two failure modes are real: in Signed::consume (signer.rs, the `let mut iter = start..end; value.receive_auth_handles(&mut iter)` block around lines 334-338) there is no leftover-handle check, so array elements keep the u32::MAX sentinel (signer.rs:31) and any Signed field serialized after the array silently consumes the array's handles — wrong-token assignment in the auth machinery, which can succeed silently if payload types coincide, or fault on the sentinel handle later. In the entrypoint path (call/encode.rs:16 contract_call_decode -> receive_auth_handles_from_slice, wired in macros/src/common/exports.rs:376), the strict leftover check converts this into a confusing 'unexpected auth handle remaining' runtime error for a type the SDK otherwise supports. The derive macro recurses per field (contract_type.rs:218/227), so any #[contract_type] struct with an array-of-Signed field hits the no-op. The asymmetry with CollectAuthHandles for [T; N] rules out this being intentional design. Severity high stands: it is silent misassignment of auth tokens (the SDK's core security primitive) in the consume path, with no compile-time, runtime, or documentation guard; the only mitigating factor is that array-of-Signed is a less common shape than Vec.

### [macros/footgun] static_key!/sha256_static! hash the source token including quotes, while hash_to_array! hashes the literal's value

**File:** `crates/macros/src/static_hash.rs:4-19`

`storage_key_static` and `sha256_static` do `let string = input.token().to_string();` — for `sha256_static!("foo")` this hashes the 5 bytes `"foo"` (quotes included), and escape sequences/raw-string syntax are hashed as written (`"\n"` hashes 4 source chars; `r"foo"` != `"foo"`). Meanwhile `sha256_array` (the `hash_to_array!` macro) uses `lit_str.value().as_bytes()` (line 56) and `sha256_ident` uses the unquoted ident text. So three sibling macros in the same file hash three different byte sequences for the same logical string: `sha256_static!("X")` != `SHA256Hash::new(hash_to_array!("X"))` != sha256 of `X` computed off-chain. Anyone reproducing a `static_key!("...")` storage key or `sha256_static!` nonce outside the macro (indexer, client, other language) will compute a different hash and silently look up the wrong key. None of this is documented (the macros have zero rustdoc).

> Verifier: All factual claims confirmed by reading crates/macros/src/static_hash.rs: storage_key_static and sha256_static hash input.token().to_string() (lines 4-19), which includes quotes and source-level escape syntax, while sha256_array/hash_to_array! hashes lit_str.value().as_bytes() (line 56) and sha256_ident hashes the bare ident — three different byte sequences for the same logical string. Empirically verified: the pinned test in crates/sdk/tests/macros.rs expects 8f27a663..., which equals sha256 of the 15-byte string '"method_called"' WITH quotes (unquoted gives f506f3f7...). The footgun is not hypothetical: hogd's native_contract_test_framework.h contains a dedicated workaround helper make_storage_key_matching_static_key_sdk_macro with the comment 'the sdk puts quotes around the string input to the static_key macro', proving an external reproducer already tripped on this and had to special-case it. The documentation claim also holds: zero rustdoc on any of the five proc-macro entry points in crates/macros/src/lib.rs, nothing on the sdk re-export (crates/sdk/src/lib.rs:166-168), no macros-crate README, and nothing in crates/sdk/doc/*.md. The type system does not prevent the confusion (sha256_static!("X") and SHA256Hash::new(hash_to_array!("X")) both produce SHA256Hash but differ in value). Severity stays high: storage-key derivation in a blockchain SDK must be reproducible off-chain (indexers, clients, other languages), the default reproduction is silently wrong, equivalent literal spellings (r"x" vs "x", escapes) produce different keys, and the behavior is now frozen by test/deployed state while remaining documented nowhere in the SDK itself.

### [native-exec/footgun] InvokeError's Display impl infinitely recurses (stack overflow on any `{}`/to_string)

**File:** `crates/native-exec/src/invoke_error.rs:14-18`

`impl fmt::Display for InvokeError { fn fmt(...) { write!(f, "InvokeError {}", self.clone()) } }` formats a clone of itself with `{}`, which calls Display again — unconditional infinite recursion. InvokeError is a public type that implements `std::error::Error`, so any user code that does `format!("{}", err)`, `err.to_string()`, or passes it through anyhow/Box<dyn Error> reporting will crash the test process with a stack overflow instead of printing the error. It clearly meant `self.error_type` (or `{:?}`). Nothing in the crate currently calls Display, which is why this has survived; the first contract author who tries to print the error they caught will hit it.

> Verifier: Confirmed by reading crates/native-exec/src/invoke_error.rs:14-18: Display::fmt does `write!(f, "InvokeError {}", self.clone())`, formatting a clone of itself with `{}`, which re-invokes the same Display impl with no base case — guaranteed infinite recursion/stack overflow (the exact pattern clippy's recursive_format_impl lint targets). InvokeError is publicly exposed (`pub mod invoke_error` in lib.rs, pub struct) and implements std::error::Error (line 20), so to_string(), format!("{}"), anyhow, or Box<dyn Error> reporting all crash. Workspace grep confirms no in-tree code currently calls Display (only Debug `{:?}` and downcasts), matching the finding's explanation for why it has gone unnoticed; that is the only mitigation, and it does not protect downstream users. ### [sdk-core/footgun] sdk::Backtrace is unsound: safe Copy type holding dangling stack pointers, dereferenced in safe Display

**File:** `crates/sdk/src/diagnostics/debug_context.rs:102-131`

Under the `debugging` feature (on by default in `dev`), `Backtrace` is exported at the crate root via `pub use diagnostics::*` (lib.rs:156). It is `#[derive(Copy, Clone)] pub struct Backtrace { top: Option<NonNull<Frame>> }` with a safe `pub fn capture()` and a safe `Display` impl that does `let frame = unsafe { frame.as_ref() };`. The safety comment says 'After a backtrace is captured, we are in the non-returning context of `abort`', but nothing enforces that: a contract author can call `Backtrace::capture()` inside a `with_debug_context` scope, return/store the Copy value, and format it after `FramesGuard::drop` pops the frames — at which point `top` points at a dead stack `Frame` local (`NonNull::from(&frame)` at line 48). That is UB reachable entirely from safe code.

> Verifier: Confirmed by direct code reading. crates/sdk/src/diagnostics/debug_context.rs:102-131 defines `#[derive(Copy, Clone)] pub struct Backtrace { top: Option<NonNull<Frame>> }` with a safe public `capture()` and a safe Display impl that does `unsafe { frame.as_ref() }`. Severity adjusted high -> medium: the API only exists under the debugging/dev feature (diagnostics tooling, not production default), the only in-tree callers (contract_op.rs:64, :86) use it correctly inside non-returning abort paths, misuse requires deliberate user action with an undocumented type, and the consequence is UB in dev/test tooling rather than a deployed-contract vulnerability.
