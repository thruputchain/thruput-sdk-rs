# ERC20 Permit

**Status:** implemented in `groundhog-erc20-permit-if`, with a worked example in
`example-contracts/permit_wallet` and `example-contracts/erc20_permit`.

Off-chain approval for ERC20 tokens: the owner signs, anyone submits. It is the
Groundhog analogue of ERC-2612, built on
[signed operations](2026-08-31-signed-operations.md) and auth tokens rather
than on address recovery, because Groundhog has no `ecrecover`: an address is
`sha256(sep || cxs({pubkey, nonce}))`, so one key controls many accounts and a
signature alone does not name one.

## Who implements what

The **owner's wallet** implements `SignedOp`. The **token** implements
`ERC20Permit`, whose methods take a signed grant token (`Signed<PermitGrant>`
or `Signed<ClearAllowanceGrant>`). The token never sees a public key, a
signature, or an `Operation`.

```text
submitter ──execute_signed_op(op, sig)──▶ wallet   consume under the owner key;
          ◀────── Signed<Opaque> ────────          mint the requested grant, consumer = request.token
          ──transfer_from_signed(grant, ─▶ token   consume → (grant, minter); owner := minter
              receiver, amount)
```

Identity comes from `Signed::consume`, which returns the minting address from
the runtime. Nothing the submitter asserts about the owner is trusted, a grant
cannot reach any contract but its named consumer, and it cannot be consumed
twice.

Taking a token rather than an operation is what keeps the interface
independent of *how* the owner authorizes. A `SignedOp` wallet is one minter;
an ERC1271 wallet, a multisig or a governance contract can mint the same grant
and the token cannot tell them apart. Rotation, multiple keys and weighted
thresholds are the minter's business; a key it no longer accepts stops
producing grants the moment it says so. Deriving an owner from the signing key
would instead pin the key the account was *created* with and keep honoring a
rotated-out one.

One limit worth stating: refusal is a throw, a throw reverts the frame, and a
reverted frame writes nothing, so a refused operation does not consume its
`(nonce, block_expiry_height)` pair. A permit signed by a former key is
refused (as `InvalidSignature`, since the wallet checks against the key it
holds) while that key is not the owner, not retired — rotate back to the key
and it is valid again. The `SignedOp` interface requires refusal to throw, so
no wallet can do better without a second mechanism (an explicit invalidate,
say).

## The payload types

`PermitRequest { token, spender, amount }` and `ClearAllowanceRequest {
token, spender }` are the bodies an owner signs. Their `TYPE_DEF`s go into the
preimage, so they are the interop contract with off-chain signers. `token` is
load-bearing: the preimage binds the verifying contract (the wallet) but not
the token, so without it a submitter could carry an approval to a different
ERC20 the owner holds. Clearing is its own type rather than a zero-amount
`PermitRequest` so the signature says which operation the owner approved.

`PermitGrant { spender, amount }` and `ClearAllowanceGrant { spender }` are
the minted tokens' payloads. They carry no owner (that is the minter address)
and no token (that is the node's named consumer, which nothing else can
consume). The token contract sees only the grants; the requests are the
contract between owner, wallet and off-chain signer. A grant redeemed at the
wrong method fails to decode as that method's type and aborts.

## A grant is a one-shot allowance

An auth token lives only as long as the transaction that minted it and is
spent by the one call that consumes it, so it is already an allowance scoped
to a single use. `transfer_from_signed(grant, receiver, amount)` spends it
directly: the caller must be `grant.spender`, `amount` may not exceed
`grant.amount` (`ExceedsGrant` otherwise), and nothing is written but the
transfer. The grant is spent whatever `amount` is. This is the path to prefer;
Ethereum has no way to hand over a capability, which is why allowances are its
substitute.

A standing allowance is still what a spender needs when it draws later, in
another transaction, or through code that only speaks `transfer_from`:

- `increase_allowance_signed(grant)` adds `grant.amount` to the allowance,
  exactly as a positive `adjust_allowance` by the owner would. Unlike
  ERC-2612's `permit`, which overwrites, two grants sum.
- `clear_allowance_signed(grant)` deletes the allowance entry under an
  exclusive lock, freeing its storage. Another transaction in the same block
  that writes the same allowance conflicts at commit rather than landing
  beside the clear.

## Wallets are per-purpose

A signature binds exactly one payload type, so a wallet serving several kinds
of signed operation needs one enum spanning all of them, and every added
variant changes that `TYPE_DEF` and retires every outstanding signature.
`default_wallet` implementing `SignedOp` was considered and rejected for that
reason; a permit wallet is its own contract, and `permit_wallet` signs a
`WalletRequest` enum spanning exactly the two permit requests.

## Replay, in two places

Replay protection is the signed-op component's: a signer-chosen, unordered
`(nonce, block_expiry_height)` pair, consumed once at the wallet (see
`2026-09-05-signed-op-uniquifier.md`). Within a block every transaction
executes against the previous block's state, so two submissions of one permit
both see the pair unconsumed and both verify. The slot is written under an
exclusive lock, so the second commit conflicts rather than landing beside the
first. Across blocks the first consumption is visible and the second fails as
`AlreadyConsumed`. `example-contracts/erc20_permit` pins both.
