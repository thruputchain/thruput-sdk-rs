# ERC20 Permit

**Status:** implemented in `groundhog-erc20-permit-if`, with a worked example in
`example-contracts/permit_wallet` and `example-contracts/erc20_permit`.

Off-chain approval for ERC20 tokens: the owner signs, anyone submits. It is the
Groundhog analogue of ERC-2612, built on
[signed operations](2026-08-31-signed-operations.md) and auth tokens rather
than on address recovery, because Groundhog has no `ecrecover`: an address is
`sha256(sep || cxs({pubkey, nonce}))`, so one key controls many accounts and a
signature alone does not name one.

## Who implements what

The **owner's wallet** implements `SignedOp`. The **token** implements
`ERC20Permit`, whose methods take a `Signed<PermitGrant>`. The token never
sees a public key, a signature, or an `Operation`.

```text
submitter ──execute_signed_op(op, sig)──▶ wallet   verify_and_spend; owner-key policy;
          ◀──── Vec<Signed<Opaque>> ─────          mint PermitGrant, consumer = op.body.token
          ──permit(grant)──────────────▶ token    consume → (grant, minter); owner := minter
```

Identity comes from `Signed::consume`, which returns the minting address from
the runtime. Nothing the submitter asserts about the owner is trusted, a grant
cannot reach any contract but its named consumer, and it cannot be consumed
twice.

Taking a token rather than an operation is what keeps the interface
independent of *how* the owner authorizes. A `SignedOp` wallet is one minter;
an ERC1271 wallet, a multisig or a governance contract can mint the same grant
and the token cannot tell them apart. Rotation, multiple keys and weighted
thresholds are the minter's business; a key it no longer accepts stops
producing grants the moment it says so. Deriving an owner from the signing key
would instead pin the key the account was *created* with and keep honoring a
rotated-out one.

One limit worth stating: refusal is a throw, a throw reverts the frame, and a
reverted frame writes nothing, so a refused operation does not spend its
nonce. A permit signed by a former key is refused while that key is not the
owner, not retired — rotate back to the key and it is valid again. The
`SignedOp` interface requires refusal to throw, so no wallet can do better
without a second mechanism (bumping nonces on rotation, say).

## The payload types

`PermitRequest { token, spender, amount }` is the signed body. Its `TYPE_DEF`
goes into the preimage, so it is the interop contract with off-chain signers.
`token` is load-bearing: the preimage binds the verifying contract (the
wallet) but not the token, so without it a submitter could carry an approval
to a different ERC20 the owner holds.

`PermitGrant { spender, amount }` is the minted token's payload. It carries no
owner (that is the minter address) and no token (that is the node's named
consumer, which nothing else can consume). The token contract sees only this
type; `PermitRequest` is the contract between owner, wallet and off-chain
signer.

## Two ways to spend

`permit` writes an allowance, to be spent later through `transfer_from`.
Matches ERC-2612 and whatever already speaks allowances.

`transfer_from_signed` moves the tokens in the same call and writes nothing.
An auth token is already a one-shot capability, so turning it into a standing
allowance makes a durable copy of authority that was meant to be spent once.
Ethereum has no way to hand over a capability, which is why allowances are its
substitute; here the allowance is the lossy step.

## Wallets are per-purpose

A signature binds exactly one payload type, so a wallet serving several kinds
of signed operation would need one enum spanning all of them, and every added
variant would change that `TYPE_DEF` and retire every outstanding signature.
The same wallet would also give every purpose one strictly sequential nonce
stream, so an unsubmitted permit stalls unrelated operations. `default_wallet`
implementing `SignedOp` was considered and rejected for both reasons; a permit
wallet is its own contract.

## Replay, in two places

Within a block every transaction executes against the previous block's state,
so two submissions of one permit both see the same nonce and both verify. The
nonce slot is written under an exclusive lock, so the second commit conflicts
rather than landing beside the first. Across blocks the first spend is visible
and the second fails as `UnexpectedNonce`. `example-contracts/erc20_permit`
pins both.
